## **二、RAG 完整执行链路**

先建立整体架构。

## **RAG Pipeline**

**1. Query**

用户问题：退款需要满足什么条件？

**2. Embedding**

将 Query 转换成向量（Vector）

**3. Retrieval**

在知识库中进行向量检索，召回 Top-K 文档

**4. Rerank**

对召回结果重新排序，选择更相关的内容

**5. Context Construction**

将最终检索内容组装成 LLM 上下文

**6. LLM Generation**

LLM 根据用户问题和检索上下文生成答案

**Final Answer**

向用户返回退款规则说明

这里有一个非常重要的认识：

**RAG 不等于向量数据库。**

向量数据库只是 Retrieval 阶段的一种实现方式。RAG 的测试必须覆盖整个知识检索与生成链路。

## **三、先理解各阶段的职责和测试边界**

| 阶段        | 主要职责      | 测试重点       |
| --------- | --------- | ---------- |
| Query     | 接收和处理用户问题 | Query 是否正确 |
| Embedding | 文本转向量     | 向量维度、输入正确性 |
| Retrieval | 从知识库召回文档  | 召回准确性、相关性  |
| Rerank    | 重新排列文档    | 排序是否正确     |
| Context   | 组织检索内容    | 内容是否完整、正确  |
| LLM       | 根据上下文生成回答 | 是否忠实于检索内容  |

特别注意：我们今天不需要自己实现一个真正的向量数据库，也不需要训练 Embedding 模型。

我们要掌握的是如何测试这些组件的输入、输出、职责边界，以及组件之间的数据传递。

## **四、向量检索的工作机制**

这是今天需要真正理解的技术重点。

### **1. 为什么需要 Embedding？**

假设电商支付知识库有以下内容：

| 文档 ID | 知识内容                 |
| ----- | -------------------- |
| D001  | 用户在订单未发货前可以申请取消订单    |
| D002  | 用户完成支付后，满足退款条件可以申请退款 |
| D003  | 订单退款通常需要经过权限校验       |
| D004  | 用户可以通过订单号查询支付状态      |

用户提问：

> 我已经付款了，现在想把钱退回来，应该怎么操作？

如果使用传统关键词搜索，可能因为用户没有使用「退款」这个关键词，导致检索效果不理想。

Embedding 的作用就是把文本转换成向量，让语义相近的文本在向量空间中具有较高的相似度。

例如：

**文本向量化示意**

用户 Query

我已经付款了，现在想把钱退回来

Embedding Model

[-0.21, 0.83, 0.15, ...]

**知识库中的文档向量**

D002：退款规则

高相关

D003：退款权限

相关

D004：支付状态

较低相关

示意结果，实际相似度取决于 Embedding 模型和检索配置。

### **2. 向量相似度如何计算？**

常见方法之一是 Cosine Similarity（余弦相似度）。

\\[ Similarity(A,B)=\frac{A\cdot B}{|A||B|} \\]

它衡量两个向量方向的接近程度。

一般情况下：

- 越接近 1：方向越相似。
- 接近 0：方向相关性较弱。
- 接近 -1：方向相反。

注意：相似度高不代表文档一定正确，也不代表它一定能够回答用户的问题。

这是 RAG 测试中非常重要的区别：

**Similarity ≠ Relevance ≠ Correctness**

### **3. Retrieval 如何工作？**

假设知识库中有 10000 个文档。

用户提出 Query 后：

1. 将 Query 转换为向量。
2. 向量数据库根据相似度寻找相关文档。
3. 按相似度排序。
4. 返回 Top-K 文档。

例如 Top-K = 3：

| 排名 | 文档        | Similarity |
| -- | --------- | ---------- |
| 1  | D002 退款规则 | 0.92       |
| 2  | D003 退款权限 | 0.87       |
| 3  | D004 支付状态 | 0.72       |

实际向量数据库可能使用 HNSW、IVF 等近似最近邻索引算法，并不一定对所有文档逐一进行精确计算。

因此，测试不能只验证是否返回了三个文档，还需要验证返回的文档是否真正符合业务问题。

## **五、如何测试 Retrieval 的准确性与相关性？**

这是 RAG 测试工程师最重要的能力之一。

我们先建立一个 Ground Truth Dataset（标准测试数据集）。

例如：

| Query       | 预期相关文档    |
| ----------- | --------- |
| 已支付订单如何退款？  | D002、D003 |
| 如何查询订单支付状态？ | D004      |
| 未发货订单如何取消？  | D001      |

这里有一个关键点：

**测试 Retrieval，必须提前定义什么是正确的检索结果。**

否则测试程序无法判断召回结果是否准确。

### **1. Precision\@K**

Precision\@K 衡量返回的 K 个文档中，有多少是真正相关的。

\\[ Precision\@K=\frac{Relevant\ Documents\ in\ TopK}{K} \\]

例如：

- Top-3 返回 D002、D003、D004。
- 标准答案是 D002、D003。

那么：

\\[ Precision\@3=\frac{2}{3}=0.667 \\]

### **2. Recall\@K**

Recall\@K 衡量所有相关文档中，有多少被成功召回。

\\[ Recall\@K=\frac{Retrieved\ Relevant}{All\ Relevant} \\]

假设标准答案有 D002、D003，而 Top-3 返回 D002、D003、D004：

\\[ Recall\@3=\frac{2}{2}=1.0 \\]

两者的区别：

- Precision：检索结果中有多少是对的？
- Recall：应该找到的内容，有多少被找到了？

真实项目中，通常还会使用 MRR、NDCG 等指标评价排序质量。

今天先掌握 Precision\@K 和 Recall\@K 即可，不需要为了掌握指标而增加不必要的学习负担。
