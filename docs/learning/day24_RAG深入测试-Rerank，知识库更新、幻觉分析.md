## **一、Rerank：为什么需要重排序？**

一个典型 RAG 检索过程：

**User Query**

已支付订单如何申请退款？

**Retriever：初步召回**

从知识库中召回 Top 10 文档

**Reranker：相关性重新评分**

对 Query 和每篇文档进行相关性评估

**重新排序后的 Top 3**

把最相关的文档交给 LLM

Retriever 和 Reranker 的职责不同：

| 模块        | 核心职责                      |
| --------- | ------------------------- |
| Retriever | 尽可能找出相关文档                 |
| Reranker  | 判断哪些文档与当前 Query 更相关，并重新排序 |

例如，Retriever 返回：

| 文档   | 内容           | 初始排名 |
| ---- | ------------ | ---- |
| D001 | 订单支付成功后的处理流程 | 1    |
| D002 | 已支付订单可以申请退款  | 2    |
| D003 | 退款需要检查订单状态   | 3    |

经过 Reranker 后：

| 文档   | 新排名 | 相关性判断    |
| ---- | --- | -------- |
| D002 | 1   | 直接回答退款问题 |
| D003 | 2   | 与退款条件相关  |
| D001 | 3   | 相关性较弱    |

**测试重点不是 Reranker 有没有执行，而是重排序结果是否符合 Query 的实际相关性。**

## **二、Rerank 应该怎么测试？**

先看一个高价值场景：

用户问：

> 已支付订单如何申请退款？

预期相关性顺序：

```
expected_order = ["D002", "D003", "D001"]
```

Reranker 实际返回：

```
actual_order = ["D002", "D001", "D003"]
```

这里不能只检查三个文档都存在，因为这只能证明文档没有丢失，不能证明排序正确。

需要关注两个维度：

- **排序质量**：相关文档是否排在不相关文档前面？
- **Top-K 质量**：最终交给 LLM 的前 K 篇文档是否包含最重要的证据？

常见的排序评估指标包括 MRR、NDCG。今天先理解它们的用途，不要求你现在实现完整评估算法：

- MRR：关注第一个相关结果排在第几位。
- NDCG：关注多个相关结果的排序质量，并考虑相关性等级。

## **三、知识库更新测试**

真实业务中，知识库不是静态的。

以电商退款规则为例：

- V1：订单支付后 7 天内可以申请退款。
- V2：退款规则调整为订单支付后 15 天内可以申请退款。

知识库更新后，RAG 必须检索到 V2，而不能继续使用 V1。

这里需要区分两个问题：

| 测试点     | 验证目标            |
| ------- | --------------- |
| 更新是否生效  | 新内容是否进入检索系统     |
| 旧内容是否失效 | 旧规则是否仍然被召回并影响回答 |

例如：

```
def test_rag_knowledge_update():    # 1. 初始化知识库，写入 V1    # 2. 查询退款规则，验证返回 V1    # 3. 更新知识库为 V2    # 4. 再次查询，验证返回 V2    # 5. 验证旧规则 V1 不再影响最终回答
```

**核心风险：知识库的数据已经更新，但向量索引没有同步更新。**

因此，不能只验证数据库中的文档内容，还要通过实际 RAG 检索链路验证更新结果。

## **四、幻觉分析：检索不足时，Agent 应该怎么办？**

这是 RAG 测试中非常重要的能力。

假设用户问：

> 我的订单退款什么时候到账？

Retriever 只检索到：

```
documents = [    "已支付订单可以申请退款",    "退款前必须验证订单归属"]
```

这些资料没有说明退款到账时间。

但 LLM 回答：

> 退款将在 24 小时内到账。

这个回答看起来合理，但没有任何检索证据支持。

测试不能只判断回答是否通顺，而要判断：

1. 检索资料是否包含回答所需的信息？
2. 回答是否超出了证据范围？
3. 证据不足时，Agent 是否明确告知用户无法确认，而不是编造具体时间？

这里有一个重要区别：

- **Faithfulness**：回答中的事实是否有上下文依据。
- **幻觉风险**：在缺少证据、证据冲突或证据过期时，模型是否仍然给出未经支持的事实。

Day 23 已经实现了基础 Faithfulness 评估。今天重点是把它放进真实业务条件中验证，而不是重新写一遍指标。
