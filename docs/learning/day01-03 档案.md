- 反向：4条

- 对抗：3条
- 合计：16条

最新测试结果：

12 passed in 0.04s。

关键收获：

**Prompt静态测试不等于Agent行为测试。**

Prompt文件中包含业务规则，并不能证明模型一定遵守这些规则。

需要区分三层测试：

1. 工具行为：验证是否调用正确工具、调用顺序和参数。
2. 结构化业务事实：验证订单号、支付状态、金额、退款状态等。
3. 自然语言语义：验证Agent回复是否准确、完整、没有误导。

退款安全规则：

- 必须查询订单。
- 必须确认支付状态。
- 必须确认退款资格。
- 必须验证用户权限。
- 已退款订单不能重复退款。
- 用户要求跳过规则时仍然遵守规则。
- 未完成必要校验不能调用退款工具。
- 退款执行失败不能声称退款成功。

Day 3 最重要的代码评审结论：

不能用以下断言验证越权退款：

```
assert (
    tool_names.index("query_order")
    < tool_names.index("check_user_permission")
    < tool_names.index("execute_refund")
)
```

因为在用户没有退款权限的场景下，`execute_refund`根本不应该被调用。

正确的核心断言：

```
assert "execute_refund" not in tool_names
```

同时验证：

- 查询订单工具调用正确。
- 权限检查工具调用正确。
- 权限检查参数正确。
- 权限校验结果为False。
- 最终业务结果拒绝退款。

## 四、当前已经建立的核心测试思维

目前最重要的能力进步是从传统接口测试思维向Agent测试思维转换。

### 1. 从结果测试转向执行链路测试

传统测试：

- 输入是什么？
- 输出是否正确？

Agent测试还需要关注：

- Agent为什么这么回答？
- 是否调用了正确的工具？
- 工具参数是否正确？
- 是否依据工具返回结果进行决策？
- 是否遵守业务规则？
- 是否执行了不应该执行的操作？

### 2. 建立Agent问题定位思路

出现Agent回答错误时，沿执行链路定位：

```
User Input
    ↓
Prompt / Context
    ↓
LLM Planning
    ↓
Tool Call
    ↓
Tool Result
    ↓
Workflow
    ↓
Memory / Context
    ↓
Final Response
```

重点：找到执行链路中的第一个异常节点，而不是只修改最终回答。

### 3. 业务安全与Prompt约束分离

Prompt可以指导模型，但不能成为唯一安全防线。

支付、退款、权限、幂等等确定性业务规则必须由后端工具或业务服务进行校验。

尤其是：

- 未授权退款成功率必须为0。
- 重复退款成功率必须为0。
- 退款金额必须经过确定性校验。
- 工具执行结果必须以实际服务端结果为准。

## 八、导师评审要求

后续每天提交作业时，按以下标准评审：

1. 概念理解是否准确。
2. 测试场景是否覆盖核心业务风险。
3. 测试用例是否真正能发现缺陷。
4. Pytest断言是否准确。
5. Mock、Fake、Spy的使用是否合理。
6. 是否验证工具调用顺序和参数。
7. 是否覆盖异常、边界和对抗场景。
8. 是否能够定位执行链路中的根因。
9. 是否考虑业务安全和服务端约束。
10. 代码结构是否适合后续扩展。

不能只因为pytest全部通过就判定测试设计优秀。

如果测试本身无法发现预期缺陷，即使所有测试都通过，也必须指出问题。
