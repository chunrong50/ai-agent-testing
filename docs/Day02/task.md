## 任务三：设计真实电商 Agent 测试场景
假设用户连续对 Agent 说：
第一轮：我的订单号是 A10086。

第二轮：帮我查一下支付状态。

第三轮：如果已经支付成功，帮我确认能不能申请退款。
第四轮：请告诉我这个订单的金额。

请思考：
1. 如果历史对话被截断，Agent 可能丢失什么信息？
2. 如果订单号丢失，Agent 是否应该自行猜测？
3. 如果支付状态丢失，是否应该直接判断可以退款？
4. 如何通过自动化测试证明关键信息没有丢失？
这里要建立一个重要意识：
上下文管理错误可能直接演变成电商支付业务错误。

我的回答：
1. 丢失订单号、支付状态、订单金额、用户提到的需要去申请退款操作，历史记录可能都丢失 
2. 不能自行猜测，必须根据用户输入内容以及工具查询的到结果反馈给用户。如果猜测就成了Agent出现了幻觉BUG
3. 不能自行判断，Agent需要提醒用户重新输入订单号，再调用tool去订单系统查询支付状态，根据tool返回的结果再告知用户订单支付状态以及后续退款操作
4. 设计用例去验证用户输入的内容和工具调用时的输入内容一致，同时工具返回的结果也包含关键信息，Agent的预留输出也需要包含关键信息。

### 逐项点评：
1. 可能丢失的信息：正确。 订单号、支付状态、金额、退款意图都可能因历史记录被截断或未被保留而丢失。还可以补充：退款资格、用户身份与权限信息、工具查询结果及其时效性。
2. 不能猜测：正确。 但要区分“信息缺失”和“幻觉”：信息缺失是上下文或数据问题；Agent在没有证据时编造订单状态，才是幻觉表现。
3. 后续处理：基本正确。 如果订单号确实已经丢失，应先向用户确认订单号，再查询订单系统。如果订单号仍在当前上下文或结构化 Memory 中，就不必让用户重复输入。支付状态也必须以工具返回的权威数据为准。
4. 测试设计：方向正确，但还不够完整。 除了验证用户输入与工具参数一致、工具返回包含关键信息，还应验证：
   - 关键订单信息是否进入模型实际收到的上下文；
   - 工具调用结果是否被正确保留和传递；
   - 预留输出空间是否足够；
   - 信息缺失时，Agent是否主动澄清，而不是编造。
建议把第 4 点升级为一条完整的测试链路：
用户输入 → 上下文构建 → Token计算 → Tool调用 → Tool返回 → 上下文更新 → 模型回答
链路：-》用户输入-》关键订单信息是否进入模型实际收到的上下文 -》检查预留空间是否足够 -》用户输入与工具参数一致 -》   工具调用结果是否被正确保留和传递-》信息缺失时，Agent是否主动澄清，而不是编造

这样你验证的就不只是某个字段，而是整条信息传递链路。

## 进阶思考：

假设模型最大上下文窗口是 8,000 Tokens，输入内容有 7,000 Tokens，预留输出 2,000 Tokens。

为什么不能直接把请求发送给模型？
请从 Token、Context Window 和输出空间三个角度解释。
模型的Context Window最大为8000Tokens，其中Context Window包含了输入内容、历史记录、用户输入、工具调用输入和输出、模型预留输出。
如果输入内容有 7,000 Tokens，预留输出 2,000 Tokens， 在不考虑工具调用的token、历史记录、系统提示词、系统限制的情况下，目前总共的Context Window：7000+2000=9000 ，9000token 已经超出了模型的最大窗口量，
因此，当上下文窗口大约模型的最大上下文窗口时，模型会进行截断，导致模型回答出现幻觉，回答错误或者偏离事实，出现编制的可能。
