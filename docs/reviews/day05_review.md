- 对于安全或权限错误，不能让 LLM 通过修改参数来绕过限制。

也就是说，可以让 LLM 帮助修正参数，但是否允许执行，始终由 Agent 和后端业务规则决定。

### 2. 退款工具内部还需要校验什么？

你提到退款金额必须和订单金额一致，这是一个很好的例子。

我再补充几个关键校验：

| 校验项      | 校验目的        |
| -------- | ----------- |
| 订单是否存在   | 防止无效订单退款    |
| 订单是否已支付  | 未支付订单不能退款   |
| 退款金额是否合理 | 防止负数、超额退款   |
| 实际可退款金额  | 防止重复退款或超额退款 |
| 用户是否有权限  | 防止越权退款      |
| 订单退款状态   | 防止重复执行退款    |

尤其要注意：退款工具应从可信的订单数据源重新读取订单金额和状态，不能只相信 LLM 传过来的参数。

### 3. 把这道题整理成面试答案

你可以这样回答：

> Agent 在调用工具之前，首先通过 Tool Schema 校验参数类型和基本约束，例如退款金额必须大于 0。
>
> 如果 Schema 校验失败，Agent 拒绝执行工具，可以将错误信息返回给 LLM 进行有限次数的修正。
>
> 即使 Schema 校验通过，退款工具内部仍然需要进行业务校验，例如订单状态、用户权限、实际可退款金额以及是否重复退款。
>
> 这样可以形成多层防护，避免仅依赖 LLM 的输出导致错误的业务操作。

### 4. 从测试角度，你需要掌握什么？

这道题可以提炼出三个高价值测试点：

1. `amount = -100`：Schema 校验失败，退款工具不能被调用。
2. `amount = 100`，但实际可退款金额只有 50：业务校验失败，不能退款。
3. Schema 校验通过，但退款执行前订单状态发生变化：工具重新校验，拒绝不符合条件的退款。

第三个场景尤其值得关注，它考察的是执行时业务状态变化，而不只是参数校验。

Day 5 核心知识点已掌握

你现在已经理解了 Tool Calling 中三层重要边界：

- 工具白名单：能不能调用这个工具？
- Schema 校验：传入的参数是否合法？
- 业务校验：当前业务状态是否真的允许执行？

这三个概念建议记牢，它们也是后续 LangGraph Agent 测试的基础。
